# Архитектура и план развития

## Роли

| Роль | Как появляется | Что делает |
|---|---|---|
| Клиент | сам регистрируется | заказывает вынос, отслеживает, оценивает |
| Курьер | заводит админ | берёт заказы своего района, выносит, отчитывается фото |
| Админ (диспетчер) | создаётся при развёртывании | распределяет заказы, разбирает проблемы, управляет тарифами, районами и людьми, смотрит отчёты |

## Жизненный цикл заказа

```
            ┌──────────── отказ курьера / снят админом ─────────────┐
            ▼                                                        │
  [new] ──взял / назначен──▶ [assigned] ──выехал──▶ [on_way] ──фото у двери──▶ [picked_up] ──фото у контейнера──▶ [done]
    │                          │   │                   │                          │
    │                          │   └──────────┬────────┴──────────────────────────┘
    ▼                          ▼              ▼
[cancelled] ◀────────── [cancelled]      [problem] ──админ──▶ new / assigned / done / cancelled
```

* Переходы описаны в `server/src/orders.js` (`TRANSITIONS`) и проверяются на сервере. Любое изменение пишется в `order_events` (кто, когда, комментарий).
* Курьер не может отметить «забран» без фото `pickup`, а «выполнен» — без фото `disposal`. Админ может закрыть заказ вручную.
* Клиент отменяет заказ сам только до выезда курьера (`new`, `assigned`).
* Курьер берёт заказы, только когда он на смене и заказ в его районе. Завершить смену, пока есть заказы в пути, нельзя.

## Модель данных

| Таблица | Назначение |
|---|---|
| `users` | все пользователи: роль, телефон, хэш пароля (scrypt), блокировка; для курьера ещё район и признак смены |
| `sessions` | токены входа (Bearer) |
| `zones` | районы обслуживания |
| `addresses` | адреса клиента (подъезд, этаж, кв., домофон, комментарий); удаляются мягко |
| `tariffs` | цена клиенту (база + доп. пакет) и выплата курьеру (база + доп. пакет) |
| `orders` | заказ: адрес, район, тариф, пакеты, дата и окно, статус, цена и выплата (фиксируются при создании), оценка, отметки времени каждого этапа |
| `order_events` | журнал статусов (аудит) |
| `order_photos` | фотоотчёт: `pickup`, `disposal`, `problem` |
| `shifts` | смены курьеров (начало/конец) — основа для табеля |

Деньги хранятся в целых рублях. Цена и выплата копируются в заказ, поэтому смена тарифа не меняет старые заказы и отчёты.

## API (кратко)

Авторизация: `Authorization: Bearer <token>`.

```
POST /api/auth/register | /api/auth/login | /api/auth/logout      GET /api/me
GET  /api/meta                       районы, тарифы, слоты
GET  /api/orders/:id                 карточка заказа + история + фото (с проверкой доступа)

# клиент
GET/POST /api/client/addresses       DELETE /api/client/addresses/:id
GET/POST /api/client/orders          POST /api/client/orders/:id/cancel | /rate

# курьер
POST /api/courier/shift/start | /shift/end
GET  /api/courier/orders/available | /orders/mine
POST /api/courier/orders/:id/take | /release | /status | /photos
GET  /api/courier/stats

# админ
GET  /api/admin/dashboard
GET  /api/admin/orders?status=&date_from=&date_to=&courier_id=&zone_id=&q=
POST /api/admin/orders/:id/assign | /status
GET/POST/PATCH /api/admin/couriers | /clients | /tariffs | /zones
GET  /api/admin/reports?from=&to=    GET /api/admin/reports/orders.csv?from=&to=
```

## Сознательные упрощения прототипа

| Сейчас | Для продакшена |
|---|---|
| Вход по телефону и паролю | SMS / звонок с кодом (SMS.ru, SMSC, Exolve), refresh-токены |
| Обновление через опрос раз в 15–20 с | WebSocket / SSE + push-уведомления (FCM / RuStore / APNs) |
| Оплата не подключена | ЮKassa / CloudPayments: привязка карты, списание после `done`, возвраты, чеки по 54-ФЗ |
| Район выбирается вручную | геокодер (Яндекс / DaData), полигоны районов, точка на карте |
| Фото на диске сервера, ссылки публичные (случайные имена) | S3-хранилище, подписанные ссылки с ограниченным сроком, ретеншн |
| SQLite | PostgreSQL + миграции |
| Веб-приложения (PWA-подобные) | нативные клиент и курьер (React Native / Flutter): камера, геолокация, офлайн-очередь фото |

## Дорожная карта

**Этап 1 — MVP для пилота в одном ЖК (этот прототип + вход по SMS, оплата, push)**

1. SMS-авторизация, онлайн-оплата и чеки.
2. Push клиенту («курьер в пути», «выполнено», фото) и курьеру («новый заказ в районе»).
3. Ежедневные слоты с лимитом заказов на окно (ёмкость курьеров).

**Этап 2 — рост**

1. Подписки: «каждый день / по будням в 20:00» — автоматическое создание заказов и регулярные списания.
2. Автораспределение: ближайший свободный курьер на смене, маршрут по нескольким адресам в одном доме или подъезде.
3. Геотрекинг курьера и проверка, что фото сделано рядом с адресом (координаты, EXIF).
4. Выплаты курьерам: самозанятые (API «Мой налог»), реестр выплат за период, штрафы и бонусы.
5. Промокоды, реферальная программа, B2B-договоры с УК/ТСЖ (оплата за весь дом).

**Этап 3 — операционка**

1. Роли внутри админки: диспетчер, бухгалтер, супервайзер района.
2. Чат клиент ↔ поддержка, разбор жалоб, компенсации.
3. Аналитика: когорты и удержание, LTV, загрузка курьеров по часам, тепловая карта заказов.
4. Раздельный сбор: отдельные тарифы на вторсырьё и сдача на переработку с отчётом клиенту.
